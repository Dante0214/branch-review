# branch-review

현재 브랜치의 변경 파일을 **팀 컨벤션 기준으로** 리뷰하는 Claude Code 플러그인.

일반적인 AI 코드 리뷰는 "일반적으로 좋은 코드"를 기준으로 삼는다. 그래서 팀이 이미 합의한 규칙을 모르고, 팀 규칙에 어긋나는 코드를 통과시키거나 팀이 의도적으로 선택한 방식을 지적한다.

이 도구는 순서를 뒤집는다. **팀 문서를 먼저 읽고, 거기 적힌 규칙으로 먼저 검사한다.** 그다음에야 일반 통념을 본다. 그리고 그 둘을 절대 섞지 않는다.

## 리포트 구조

```
1. 변경점 요약        브랜치·규모·무엇을 했는지
2. 컨벤션 위반        팀 문서에 근거가 있는 지적    [필수] [권장]
3. 개선 제안          일반 통념에 근거가 있는 지적  [제안]
4. 총평              머지 가능 여부 + 잘 된 점
```

2번과 3번을 나누는 것이 이 도구의 전부다.

2번은 팀 문서의 한 줄을 그대로 인용한다. 반박하려면 문서를 고쳐야 한다. 3번은 그냥 다르게 판단하면 그만이다. 이 둘이 한 목록에 섞이면 받는 쪽은 전부 "리뷰어 의견"으로 읽고, 진짜 규칙 위반까지 협상 대상이 된다.

## 설치

```
/plugin marketplace add Dante0214/branch-review
/plugin install branch-review@branch-review
```

로컬 체크아웃으로 설치하려면:

```
/plugin marketplace add /path/to/branch-review
/plugin install branch-review@branch-review
```

설치 후 `/reload-plugins`로 반영한다.

## 사용법

리뷰할 레포 안에서:

```
/branch-review:review                        # 현재 브랜치 전체
/branch-review:review --staged               # 커밋 직전, 스테이징된 것만
/branch-review:review --base origin/main     # 비교 기준 직접 지정
/branch-review:review --files-only           # 규모만 먼저 확인
/branch-review:review -- src/main/java       # 경로 제한
```

이름이 겹치지 않으면 `/review`로 줄여 써도 된다.

평문으로 말해도 동작한다 — "브랜치 리뷰해줘", "PR 올리기 전에 컨벤션 확인해줘".

## 옵션

| 플래그 | 설명 |
|---|---|
| `--base <ref>` | 비교 기준 브랜치. 기본은 `origin/dev` → `origin/develop` → `origin/main` → `origin/master` 순 자동 탐지 |
| `--staged` | 스테이징된 변경만 대상 |
| `--files-only` | diff 없이 변경 파일 목록만 |
| `--max-lines <n>` | diff 출력 상한. 기본 1500 |
| `--no-exclude` | lock 파일·빌드 산출물 기본 제외 해제 |
| `-- <경로>...` | 대상 경로 제한 |

## 리뷰 기준을 어디서 읽는가

우선순위 순서다. 위쪽이 아래쪽을 이긴다.

| 우선순위 | 파일 | 역할 |
|---|---|---|
| 1 | `.claude/review-rules.md` | 리뷰 전용 규칙. 있으면 최우선 |
| 2 | `CLAUDE.md`, `AGENTS.md`, `CONTRIBUTING.md` | 프로젝트 문서. 전용 규칙이 없을 때 여기서 추출 |
| 3 | `.prettierrc`, `.editorconfig`, ESLint, Spotless 설정 | **지적하지 말아야 할 것**을 판별하는 용도 |

3번의 쓸모가 덜 뻔하다. 포매터가 저장할 때 자동으로 고치는 항목(세미콜론, 따옴표, 들여쓰기, import 정렬)은 리뷰에서 빼야 한다. 사람이 손댈 필요가 없는 걸 지적하면 리뷰 전체가 소음으로 읽힌다.

**CLAUDE.md가 이미 있으면 별도 설정 없이 바로 동작한다.** 전용 규칙 파일은 리뷰 강도를 따로 조정하고 싶을 때만 만들면 된다.

### 전용 규칙 파일 만들기

```bash
mkdir -p .claude
cp <플러그인경로>/skills/review/templates/review-rules.md .claude/review-rules.md
```

작성 원칙은 하나다. **코드만 보고 O/X로 답할 수 있는 문장만 적는다.**

| 적는다 | 적지 않는다 |
|---|---|
| `any` 금지, 불가피하면 `unknown` + 좁히기 | 가독성 좋게 작성한다 |
| import는 절대경로 `@/`, `../../` 금지 | 적절히 분리한다 |
| 엔티티를 컨트롤러 응답에 직접 노출 금지 | 성능을 고려한다 |

판정할 수 없는 문장은 리뷰에서 무시되므로 적을 필요가 없다.

## 심각도

| 표기 | 뜻 | 근거 |
|---|---|---|
| `[필수]` | 머지 전에 고친다 | 문서에 "금지"·"반드시"로 적혔거나 동작이 깨짐 |
| `[권장]` | 고치는 편이 맞다 | 컨벤션 위반이나 동작에는 지장 없음 |
| `[제안]` | 판단은 작성자 몫 | 컨벤션 밖의 개선 아이디어 |

총평의 머지 가능 여부는 **가능** / **수정 후 가능** / **재작업 필요** 셋 중 하나다.

## 설계 원칙

- **읽지 않은 코드는 리뷰하지 않는다.** diff가 상한에 걸려 잘리면 파일을 직접 열거나, 못 봤다고 밝힌다. 잘린 자리를 추측으로 메우면 없는 결함을 지어낸다.
- **근거 없는 지적은 버린다.** 문서를 인용하지도 못하고 실패 시나리오도 못 대면 그건 취향이다.
- **건수를 채우지 않는다.** 깨끗하면 "위반 없음"이 정답이다. 억지 지적 하나가 진짜 지적 열 개의 신뢰를 깎는다.
- **파일을 수정하지 않는다.** 읽기 전용이다. 사용자가 명시적으로 요청할 때만 고친다.

## 요구사항

- `git`
- `bash` — macOS·Linux 기본 탑재. Windows는 Git for Windows에 포함
- 리뷰 기준이 될 문서 최소 하나 (`CLAUDE.md`면 충분)

## 잘 동작하지 않는다면

- **`No such file or directory`로 수집이 실패한다** — `CLAUDE_PLUGIN_ROOT`가 비어 있는 환경이다. 스킬이 PATH 런처(`branch-review-collect`)와 플러그인 캐시 경로를 차례로 시도하므로 대개 그대로 진행된다. 셋 다 실패하면 설치가 깨진 것이니 `/plugin`으로 재설치한다.
- **변경 없음으로 나온다** — 비교 기준이 잘못 잡혔을 수 있다. `--files-only`로 `base`와 분기점을 확인하고, 필요하면 `--base`로 지정한다.
- **기준 파일을 못 찾는다** — 레포 루트에서 실행했는지 확인한다. 스크립트는 `git rev-parse --show-toplevel` 기준으로 찾는다.
- **diff가 잘린다** — 기본 상한 1500줄이다. `--max-lines`를 올리거나 `-- <경로>`로 범위를 좁힌다. 리뷰는 한 번에 좁은 범위를 보는 편이 정확하다.
