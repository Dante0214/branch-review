# 기획서 — branch-review

## 문제

AI 코드 리뷰 도구는 이미 여럿 있다. 팀 프로젝트 Pulse도 두 레포 모두 CodeRabbit을 붙여 뒀다. 그런데 리뷰를 받아 보면 이런 지적이 섞여 온다.

- 세미콜론과 따옴표 지적 — Prettier가 저장할 때 이미 고치는 항목이다
- "`interface` 대신 `type`을 쓰는 게 좋습니다" — 팀 CLAUDE.md는 props에 `interface`를 쓰라고 정해 두었다
- 컨트롤러에 로직이 들어간 것은 그냥 지나감 — 팀이 금지한 항목인데 도구는 모른다

원인은 하나다. **기준이 팀 밖에 있다.** 도구는 "일반적으로 좋은 코드"를 알지만 "이 팀이 합의한 코드"는 모른다. 그래서 팀이 이미 해결한 문제를 다시 꺼내고 팀이 진짜 신경 쓰는 규칙은 놓친다.

지적의 무게가 전부 같아 보이는 것은 더 나쁘다. 협상 불가능한 규칙 위반과 리뷰어 취향이 한 목록에 나란히 오면, 받는 쪽은 둘을 구분할 방법이 없다. 결국 전부 "참고 의견"으로 읽고 넘긴다. 진짜 위반까지 같이 묻힌다.

## 해결

기준을 팀 안으로 가져온다. 지적은 근거의 출처에 따라 두 층으로 나눈다.

| | 1차 | 2차 |
|---|---|---|
| 근거 | 팀이 문서로 합의한 규칙 | 일반적인 통념 |
| 인용 | 문서 원문 그대로 | 실패 시나리오 |
| 반박 방법 | 문서를 고친다 | 다르게 판단하면 된다 |

이 구분이 도구의 전부다. 나머지는 이 구분을 지키는 장치다.

## 리뷰 기준을 어떻게 정했는가

과제의 핵심 요건이 여기다. 기준을 새로 만들지 않고 **팀이 이미 쓰고 있는 문서를 기준으로 승격**시켰다.

Pulse 팀은 두 레포 모두 `CLAUDE.md`에 컨벤션을 정리해 두었다. 커밋 형식, 브랜치 네이밍, 금지 문법, 레이어 분리 원칙이 이미 문장으로 적혀 있다. 새 규칙 문서를 만들면 이 문서와 어긋나기 시작하고 둘 중 어느 것이 진짜인지 아무도 모르게 된다.

### 기준 파일의 우선순위

| 순위 | 파일 | 역할 |
|---|---|---|
| 1 | `.claude/review-rules.md` | 리뷰 전용 규칙. 강도를 따로 조정하고 싶을 때만 만든다 |
| 2 | `CLAUDE.md`, `AGENTS.md`, `CONTRIBUTING.md` | 이미 있는 프로젝트 문서 |
| 3 | `.prettierrc`, `.editorconfig`, ESLint, Spotless | **지적하지 말아야 할 것**의 목록 |

3번이 덜 뻔한 쪽이다. 포매터가 강제하는 항목은 사람이 손댈 필요가 없으므로 리뷰에서 빼야 한다. 자동으로 고쳐지는 것을 지적하면 리포트 전체가 소음으로 읽힌다. 도구 설정 파일은 무엇을 검사할지가 아니라 **무엇을 검사하지 않을지**를 알려준다.

### 판정 가능한 문장만 규칙으로 쓴다

문서의 모든 문장이 규칙은 아니다. 기준은 하나다. **코드만 보고 O/X를 낼 수 있는가.**

| 문서의 문장 | 규칙인가 |
|---|---|
| "`any`는 금지, 불가피하면 `unknown` + 좁히기" | O |
| "import는 절대경로 `@/`, `../../` 금지" | O |
| "컨트롤러에 비즈니스 로직을 넣지 않는다" | O |
| "가독성 좋게 작성한다" | X |
| "성능을 고려한다" | X |

판정할 수 없는 문장은 1차에서 뺀다. 관련된 실제 문제를 발견하면 2차로 낸다.

### 심각도

| 표기 | 조건 |
|---|---|
| `[필수]` | 문서에 "금지"·"반드시"로 적혔거나 동작이 깨짐 |
| `[권장]` | 위반이지만 동작에 지장 없음 |
| `[제안]` | 컨벤션 밖의 개선 아이디어 |

## 리포트 구조

네 부분을 항상 같은 순서로 낸다. 해당 없는 부분도 "없음"이라고 적는다. 구조가 고정되어야 리뷰끼리 비교가 되고 팀에 같은 지적이 반복되는지 보인다.

```
1. 변경점 요약     브랜치·규모·무엇을 했는지
2. 컨벤션 위반     [필수] [권장]
3. 개선 제안       [제안]
4. 총평           머지 가능 여부 + 잘 된 점
```

## 범위

**하는 것**

- 현재 브랜치의 변경분 수집 (분기점부터 워킹트리까지)
- 팀 문서에서 판정 가능한 규칙 추출
- 두 층으로 나눈 리포트 출력

**하지 않는 것**

- 파일 수정 — 읽기 전용이다. 사용자가 따로 요청할 때만 고친다
- CI 통합 — 로컬에서 PR 올리기 직전에 쓰는 도구다
- 정적 분석 재구현 — ESLint·Spotless가 하는 일을 다시 하지 않는다

## 성공 기준

- 팀 문서에 근거가 있는 지적을 **문서 원문 인용과 함께** 낸다
- 포매터가 잡는 항목이 리포트에 **없다**
- 깨끗한 브랜치에는 "위반 없음"을 낸다. 건수를 채우지 않는다
- 실제 팀 브랜치에서 사람이 못 본 문제를 최소 하나 찾는다

마지막 항목은 실제로 확인했다. `docs/sample-review.md`에 결과가 있다. 주석에 적힌 의도와 구현이 어긋난 곳을 하나, 커밋 메시지가 정리했다고 한 작업이 실제로는 안 돼 있는 곳을 하나 찾았다.

## 왜 Claude Code 플러그인인가

리뷰에는 diff만으로 부족한 판단이 있다. "이 함수가 이미 있는가"를 알려면 레포를 검색해야 하고 "이 변경이 다른 파일을 깨뜨리는가"를 알려면 호출부를 찾아야 한다. 정규식으로 짠 린터는 이걸 못 한다.

Claude Code는 리뷰 도중에 파일을 열고 검색할 수 있다. 수집 스크립트는 사실만 모으고 판단은 스킬 문서가 정한 절차대로 모델이 한다. 스크립트가 짧은 이유가 여기 있다.
