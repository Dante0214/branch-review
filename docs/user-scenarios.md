# 유저 시나리오 — branch-review

## 사용자

| | 누구 | 언제 쓰는가 |
|---|---|---|
| A | 기능을 다 만들고 PR을 올리려는 팀원 | 커밋 직후, PR 생성 직전 |
| B | 이번 주에 합류한 팀원 | 첫 작업 브랜치를 만든 뒤 |
| C | 남의 PR을 리뷰해야 하는 팀원 | 리뷰 요청을 받은 직후 |
| D | 컨벤션 문서를 관리하는 사람 | 스프린트가 끝날 무렵 |

---

## 시나리오 A — PR 올리기 직전 셀프 체크

**상황.** 안치호는 실시간 결과 화면을 사흘에 걸쳐 만들었다. 커밋 열두 개가 쌓였고 이제 PR을 올리려 한다. 그런데 사흘 전에 쓴 코드가 팀 컨벤션에 맞는지 기억이 흐리다. CLAUDE.md를 다시 읽자니 400줄이다. 그중 이번 변경에 걸리는 규칙이 몇 개인지도 모른다.

**동작.**

```
$ /branch-review:review
```

도구는 `origin/dev`와 갈라진 지점을 찾아 변경 파일 6개와 커밋 12개를 모은다. 같은 레포의 `CLAUDE.md`를 읽어 판정 가능한 규칙을 추린다. `.prettierrc`와 `.githooks/commit-msg`도 읽어 이미 자동으로 강제되는 항목은 리뷰 대상에서 뺀다.

**결과.** 컨벤션 위반 1건과 개선 제안 3건이 나온다. 커밋 형식은 훅이 이미 막고 있어 따로 언급하지 않는다.

받은 리포트에서 `[필수]`가 0건임을 확인하고 PR을 올린다. `[제안]`으로 나온 heading 태그 두 줄은 태그만 바꾸면 되므로 같이 고쳐서 커밋한다.

**이 시나리오가 없으면.** PR을 올린 뒤 리뷰어가 같은 지적을 한다. 지적을 받고 고치고 다시 푸시하는 데 반나절이 걸린다. 그사이 리뷰어는 다른 일로 넘어가 있어서 재리뷰가 다음 날로 밀린다.

---

## 시나리오 B — 새로 합류한 팀원의 컨벤션 학습

**상황.** 김효인은 이번 주에 팀에 들어왔다. CLAUDE.md를 읽긴 했지만 400줄을 한 번에 외울 수는 없다. 첫 기능을 만들면서 "이게 맞나" 싶은 순간이 계속 온다.

**동작.** 작은 단위로 커밋할 때마다 스테이징된 것만 검사한다.

```
$ /branch-review:review --staged
```

**결과.** 규칙 위반이 나올 때마다 근거로 CLAUDE.md의 해당 문장을 그대로 인용한다.

> 근거: CLAUDE.md 코드 규칙 — "import는 **절대경로 `@/`**를 사용해야 합니다. 2단계 이상 상대경로(`../../`)는 금지합니다."

문서 어디에 무엇이 적혀 있는지가 지적과 함께 온다. 규칙을 외우는 대신 걸릴 때마다 원문을 보게 되고 두세 번 반복되면 손에 붙는다.

**이 시나리오가 없으면.** 컨벤션을 모르는 채로 큰 PR을 올리고 리뷰에서 스무 개짜리 지적 목록을 받는다. 신규 합류자에게는 이게 꽤 아프다.

---

## 시나리오 C — 리뷰어의 1차 스크리닝

**상황.** 리뷰 요청이 왔다. 파일 열두 개에 400줄이다. 지금 자기 작업 중이라 시간을 길게 낼 수 없다.

**동작.** 해당 브랜치를 받아서 돌린다.

```
$ git fetch origin && git switch feature/74-public-report-page
$ /branch-review:review
```

**결과.** 컨벤션 위반은 도구가 먼저 잡아 준다. 리뷰어는 기계가 못 보는 것에 시간을 쓴다. 이 기능이 요구사항을 맞게 구현했는가, 이 설계가 다음 스프린트의 SSE 전환을 막지 않는가 같은 것들이다.

**이 시나리오가 없으면.** 리뷰어의 시간 절반이 `any` 하나 찾는 데 들어간다. 정작 설계 문제는 리뷰 끝날 때쯤 지쳐서 못 본다.

---

## 시나리오 D — 컨벤션 문서 자체의 개선

**상황.** 스프린트가 끝나 간다. 리뷰 리포트가 쌓였는데 `[제안]` 항목에 같은 지적이 반복된다. `useEffect` 정리 함수 누락이 세 번 나왔다.

**동작.** 반복되는 항목을 팀 규칙으로 승격한다.

```bash
cp <플러그인>/skills/review/templates/review-rules.md .claude/review-rules.md
```

"이 프로젝트에서 특히 주의할 것"에 한 줄을 넣는다.

```markdown
- 폴링·구독을 거는 `useEffect`는 정리 함수를 반환합니다. 이 화면들은 참가자가 빠르게 오가는 QR 진입 경로라 타이머가 중첩됩니다.
```

**결과.** 다음 리뷰부터 이 항목은 `[제안]`이 아니라 `[권장]`으로 올라온다. 근거도 "일반적으로 좋다"가 아니라 팀 문서 인용으로 바뀐다.

**이 시나리오가 왜 중요한가.** 이 도구의 최종 목적은 지적을 많이 하는 것이 아니라 **팀 규칙을 실제로 쓰이는 상태로 유지하는 것**이다. 2차에서 반복되는 항목은 팀이 아직 말로만 공유하고 문서화하지 않은 규칙이라는 신호다. 리뷰가 그 신호를 모아 준다.

---

## 흐름 요약

```
작업 → 커밋 → [리뷰] → 수정 → PR → 사람 리뷰 → 머지
                ↓
         반복되는 [제안]
                ↓
         .claude/review-rules.md 갱신
                ↓
         다음 리뷰부터 [권장]으로 승격
```

앞의 고리는 개인의 작업 품질을 올리고 뒤의 고리는 팀 규칙을 갱신한다. 두 번째 고리가 도는 팀에서는 리뷰가 지적 도구가 아니라 합의 도구가 된다.

---

## 실패하는 경우

| 상황 | 도구의 동작 |
|---|---|
| 기준 문서가 하나도 없음 | 리뷰를 멈추고 템플릿 복사를 안내한다. 기준 없는 리뷰는 취향 표명이다 |
| diff가 상한을 넘음 | 잘렸다는 사실을 알리고 생략된 파일명을 나열한다. 필요하면 직접 열어 읽는다 |
| `main`/`dev`에서 직접 작업 중 | 경고를 띄운다. 대부분의 팀에서 이것 자체가 컨벤션 위반이다 |
| git 레포가 아님 | 실행을 중단하고 알린다 |

마지막 두 줄이 중요하다. 도구가 조용히 빈 결과를 내면 사용자는 "문제가 없구나"로 읽는다. 검사하지 못한 것과 검사했는데 깨끗한 것은 다르다. 그 차이를 반드시 말해야 한다.
