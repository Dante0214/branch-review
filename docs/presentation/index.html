3주차 미니 프로젝트 · 코드 리뷰 도구

branch-review

팀 컨벤션을 먼저 보는 코드 리뷰 도구.
규칙 위반과 리뷰어 취향을 같은 칸에 넣지 않는다.

안치호 · Claude Code 플러그인

1
문제

AI 리뷰 도구는 우리 팀 규칙을 모른다

팀 프로젝트 Pulse는 두 레포 모두 CodeRabbit을 붙여 두었다. 그런데 리뷰를 받아 보면 이런 것들이 섞여 온다.

이미 해결된 것을 지적

세미콜론·따옴표 — Prettier가 저장할 때 이미 고친다

팀 결정과 반대로 지적

interface 대신 type을 쓰라고 함 — 팀은 props에 interface로 정했다

진짜 위반은 통과

컨트롤러에 로직이 들어간 것 — 팀이 금지한 항목인데 모른다

원인은 하나다. 기준이 팀 밖에 있다.

2
문제

더 나쁜 것 — 지적의 무게가 전부 같아 보인다

// 리뷰 결과

- any 타입을 쓰지 마세요
- 변수명을 더 명확하게
- 컨트롤러에 로직이 있습니다
- 세미콜론 누락
- 이 함수는 분리하는 게 좋습니다
- 주석을 추가해 주세요

협상 불가능한 규칙 위반과 취향이 나란히 있다

받는 쪽은 둘을 구분할 방법이 없다.

그래서 전부 "참고 의견"으로 읽고 넘긴다.

진짜 규칙 위반까지 같이 묻힌다.

3
해결

근거의 출처로 두 층을 나눈다

1차 — 컨벤션 위반 2차 — 개선 제안
근거 팀이 문서로 합의한 규칙 일반적인 통념
인용 문서 원문 그대로 실패 시나리오
반박 방법 문서를 고친다 다르게 판단하면 된다
표기 필수권장 제안

이 구분이 도구의 전부다. 나머지는 이 구분을 지키기 위한 장치다.

4
리뷰 기준 선정

기준을 새로 만들지 않고, 팀 문서를 승격시켰다

Pulse 팀은 이미 CLAUDE.md에 커밋 형식·브랜치 네이밍·금지 문법·레이어 분리를 문장으로 적어 두었다. 새 규칙 문서를 만들면 둘 중 어느 것이 진짜인지 아무도 모르게 된다.

순위파일역할
1 .claude/review-rules.md 리뷰 전용 규칙. 강도를 따로 조정할 때만 만든다
2 CLAUDE.md · AGENTS.md 이미 있는 프로젝트 문서에서 추출
3 .prettierrc · ESLint · Spotless 지적하지 말아야 할 것의 목록

3번이 덜 뻔하다. 포매터가 자동으로 고치는 항목을 사람에게 시키면 리포트 전체가 소음으로 읽힌다.

5
리뷰 기준 선정

판정 가능한 문장만 규칙으로 쓴다

문서의 모든 문장이 규칙은 아니다. 기준은 하나 — 코드만 보고 O/X를 낼 수 있는가.

규칙이다

  • any 금지, 불가피하면 unknown + 좁히기
  • import는 절대경로 @/, ../../ 금지
  • 컨트롤러에 비즈니스 로직 금지
  • 엔티티를 응답에 직접 노출 금지

규칙이 아니다

  • 가독성 좋게 작성한다
  • 적절히 분리한다
  • 성능을 고려한다

판정할 수 없으면 1차에서 뺀다. 실제 문제를 찾았다면 2차로 낸다.

4부 고정 구조

규칙을 도구에 넣지 않은 이유

규칙이 플러그인 안에 있으면 팀마다 플러그인을 고쳐야 하고, 규칙이 바뀔 때마다 재배포해야 한다. 규칙은 팀 레포에 두고 도구는 읽기만 한다.

스크립트가 판단하지 않는 이유

"이 유틸이 이미 있는가"를 알려면 레포를 검색해야 한다. CLAUDE.md의 자연어 규칙은 정규식으로 옮길 수 없다.

실제 적용 · 결과

사람이 못 본 두 가지를 찾았다

제안 ?submitted=1이 URL에 영구히 남는다

배너를 떼는 코드가 레포에 없다(router.replace 사용처 0). 링크를 저장했다 다시 열면 "소감이 등록되었어요"가 또 뜬다.

정작 같은 파일 주석이 "며칠 뒤 다시 열었을 때 안내가 뜨면 안 된다"는 이유로 이 방식을 골랐다고 적고 있다. 의도와 구현이 어긋난 경우다.

제안 h1 다음이 바로 h3

커밋 본문에 "heading order를 정리했다"고 적혀 있는데 h2가 없다. axe heading-order 위반이다. 커밋 메시지의 주장과 실제 코드가 어긋난 경우다.

9
실제 적용 · 결과

지적하지 않은 것이 리포트를 짧게 만든다

리포트에서 빠진 것

  • 커밋 12개의 형식 — .githooks/commit-msg가 이미 강제한다
  • 따옴표·세미콜론·줄바꿈 — Prettier가 관리한다
  • import 정렬 — ESLint 규칙이 있다

지적할 수 있었지만 하지 않았다.

최종 결과

필수0건
권장1건 — 공개 페이지 SSR 원칙
제안3건 — 접근성·상태 관리

405줄 추가에 지적 4건. 이 브랜치는 실제로 컨벤션을 잘 지켰다. 건수를 채웠다면 리포트 전체의 신뢰가 깎였을 것이다.

10
설계 원칙

안 하기로 정한 것들

원칙막는 것
읽지 않은 코드는 리뷰하지 않는다 diff가 1500줄에서 잘리면 생략된 파일명을 남긴다. 잘린 자리를 추측으로 메우면 없는 결함을 지어낸다
근거 없는 지적은 버린다 문서 인용도 못 하고 실패 시나리오도 못 대면 그건 취향이다
건수를 채우지 않는다 깨끗하면 "위반 없음"이 정답이다. 억지 지적 하나가 진짜 지적 열 개의 신뢰를 깎는다
파일을 수정하지 않는다 읽기 전용. 사용자가 따로 요청할 때만 고친다
정적 분석을 재구현하지 않는다 ESLint·Spotless가 하는 일을 다시 하지 않는다

2차에서 반복되는 항목은 팀이 아직 말로만 공유하고 문서화하지 않은 규칙이라는 신호다.

도구의 최종 목적은 지적을 많이 하는 것이 아니라, 팀 규칙을 실제로 쓰이는 상태로 유지하는 것이다. 이 고리가 도는 팀에서 리뷰는 지적 도구가 아니라 합의 도구가 된다.
