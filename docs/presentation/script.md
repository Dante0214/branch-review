# 발표 대본 · 시연 대본

## 발표 대본 (약 7분)

슬라이드 번호별 말할 내용이다. 슬라이드에 적힌 문장을 그대로 읽지 않도록, 슬라이드는 뼈대만 두고 살은 말로 붙인다.

### 1. 표지 — 20초

3주차 주제가 코드 리뷰 도구였습니다. 저는 `branch-review`라는 Claude Code 플러그인을 만들었습니다. 현재 브랜치의 변경 파일을 팀 컨벤션 기준으로 리뷰해 주는 도구입니다.

한 문장으로 하면, **규칙 위반과 리뷰어 취향을 같은 칸에 넣지 않는 리뷰 도구**입니다.

### 2. 문제 — 50초

AI 코드 리뷰 도구는 이미 많습니다. 저희 팀 Pulse도 두 레포 모두 CodeRabbit을 붙여 놨습니다.

그런데 받아 보면 이런 게 섞여 옵니다. 세미콜론 지적이 오는데, Prettier가 저장할 때 이미 고치는 항목입니다. `interface` 대신 `type`을 쓰라는 지적도 왔는데, 저희 팀 CLAUDE.md는 props에는 `interface`를 쓰라고 정해 놨습니다. 반대로 컨트롤러에 로직이 들어간 건 그냥 지나갑니다. 저희가 금지한 항목인데 도구가 모르니까요.

원인은 하나입니다. **기준이 팀 밖에 있습니다.** 도구는 "일반적으로 좋은 코드"는 알지만 "우리 팀이 합의한 코드"는 모릅니다.

### 3. 더 나쁜 문제 — 40초

그런데 더 큰 문제가 있습니다. 지적의 무게가 전부 같아 보인다는 겁니다.

여기 보시면 `any`를 쓰지 말라는 것과 변수명을 더 명확하게 하라는 게 나란히 있습니다. 앞의 것은 팀이 금지한 항목이고 뒤의 것은 의견입니다. 그런데 받는 사람은 둘을 구분할 방법이 없습니다.

그러면 어떻게 되냐면, **전부 참고 의견으로 읽고 넘깁니다.** 진짜 규칙 위반까지 같이 묻힙니다.

### 4. 해결 — 40초

그래서 근거의 출처로 층을 나눴습니다.

1차는 팀이 문서로 합의한 규칙입니다. 근거로 문서 원문을 그대로 인용합니다. 반박하려면 문서를 고쳐야 합니다.

2차는 일반적인 통념입니다. 근거로 실패 시나리오를 댑니다. 그냥 다르게 판단하면 그만입니다.

이 구분이 이 도구의 전부입니다. 나머지는 전부 이 구분을 지키기 위한 장치입니다.

### 5. 리뷰 기준 — 60초

과제 요건에 "코드 리뷰 기준 선정"이 있었는데, 저는 기준을 새로 만들지 않았습니다. **팀이 이미 쓰고 있는 문서를 기준으로 승격시켰습니다.**

저희 팀은 두 레포 모두 CLAUDE.md에 커밋 형식, 브랜치 네이밍, 금지 문법, 레이어 분리를 이미 문장으로 적어 놨습니다. 여기서 새 규칙 문서를 만들면 둘이 어긋나기 시작하고, 어느 게 진짜인지 아무도 모르게 됩니다.

우선순위는 셋입니다. 리뷰 전용 규칙 파일이 있으면 최우선, 없으면 CLAUDE.md에서 추출합니다.

세 번째가 좀 덜 뻔한데요. Prettier나 ESLint 설정은 **지적하지 말아야 할 항목을 판별하는 데** 씁니다. 포매터가 저장할 때 자동으로 고치는 걸 사람한테 시키면 리포트 전체가 소음으로 읽힙니다.

### 6. 판정 가능한 문장 — 40초

문서에 있는 모든 문장이 규칙은 아닙니다. 기준은 하나입니다. **코드만 보고 O, X를 낼 수 있는가.**

"`any` 금지"는 규칙입니다. 코드에 있거나 없거나 둘 중 하나니까요. "가독성 좋게 작성한다"는 규칙이 아닙니다. 판정을 못 합니다.

판정 못 하는 문장은 1차에서 뺍니다. 관련된 실제 문제를 발견하면 그건 2차로 냅니다.

### 7. 구조 — 40초

구조는 단순합니다. 스크립트가 사실만 모으고, 판단은 스킬 문서가 정한 절차대로 모델이 합니다.

규칙을 도구 안에 안 넣은 이유가 있습니다. 플러그인에 규칙을 박으면 팀마다 플러그인을 고쳐야 하고, 규칙 바뀔 때마다 재배포해야 합니다. 규칙은 팀 레포에 두고 도구는 읽기만 합니다.

스크립트가 판단을 안 하는 이유도 있습니다. "이 유틸이 이미 있나"를 알려면 레포를 검색해야 하고, CLAUDE.md의 "컨트롤러에 비즈니스 로직을 넣지 않는다" 같은 자연어 규칙은 정규식으로 못 옮깁니다.

### 8. 실제 적용 — 30초

만들고 나서 저희 팀 브랜치에 그대로 돌려 봤습니다. 제가 이번 주에 작업한 실시간 결과 화면 브랜치입니다. 파일 6개, 405줄 추가, 커밋 12개짜리입니다.

도구가 `origin/dev`와의 분기점을 자동으로 찾고, CLAUDE.md를 기준으로 잡고, Prettier와 커밋 훅 설정을 제외 목록으로 읽었습니다.

### 9. 결과 — 60초

두 개를 찾았는데 둘 다 성격이 비슷합니다.

첫 번째. 소감을 제출하면 `?submitted=1`을 붙여서 결과 화면으로 보내고, 그 값으로 "등록되었어요" 배너를 띄웁니다. 그런데 이 값을 URL에서 떼는 코드가 레포 전체에 없습니다. 그래서 그 상태로 링크를 저장했다가 다음 날 열면 배너가 또 뜹니다.

재밌는 건, 같은 파일 주석에 "며칠 뒤 다시 열었을 때 안내가 뜨면 방금 낸 것처럼 읽힌다"고 적혀 있다는 겁니다. 그걸 피하려고 이 방식을 골랐는데 결과적으로 피하려던 상황이 그대로 재현됩니다.

두 번째. `h1` 다음이 바로 `h3`입니다. `h2`가 없습니다. 그런데 커밋 메시지 본문에는 "heading order를 정리했다"고 적혀 있습니다.

**둘 다 코드만 봐서도, 주석만 봐서도 안 보입니다.** 겹쳐 읽어야 드러납니다.

### 10. 지적하지 않은 것 — 40초

이것도 결과의 일부라고 생각합니다.

커밋 12개가 전부 Conventional Commits 형식인데 리포트에 언급이 없습니다. 커밋 훅이 애초에 강제하니까요. 따옴표나 세미콜론도 없습니다. Prettier가 관리하니까요.

최종 결과는 필수 0건, 권장 1건, 제안 3건입니다. 405줄에 4건이면 적은데, 이 브랜치가 실제로 컨벤션을 잘 지켰습니다. 여기서 건수를 채웠으면 리포트 전체의 신뢰가 깎였을 겁니다.

### 11. 안 하기로 한 것 — 30초

만들면서 안 하기로 정한 것들입니다.

특히 첫 번째가 중요한데요. diff가 1500줄에서 잘리면 생략된 파일 이름을 남기고, 그 파일은 직접 열어 읽거나 못 봤다고 밝히게 했습니다. 잘린 diff로 리뷰하면 모델이 없는 결함을 지어냅니다.

### 12. 확장 — 30초

마지막으로, 이 도구가 궁극적으로 뭘 하려는 건지입니다.

2차 제안에 같은 항목이 반복해서 나오면, 그건 팀이 아직 말로만 공유하고 문서화하지 않은 규칙이라는 신호입니다. 그때 규칙 파일에 한 줄 추가하면 다음부터는 권장으로 올라옵니다.

리뷰가 지적 도구가 아니라 **합의 도구**가 되는 겁니다.

### 13. 정리 — 20초

정리하면 기준은 팀 CLAUDE.md를 그대로 승격했고, 구조는 근거의 출처로 두 층을 나눴고, 팀 브랜치 405줄에서 의도와 구현이 어긋난 2건을 찾았습니다.

감사합니다.

## 시연 영상 대본 (약 3분)

화면 녹화 기준이다. 터미널 폰트를 키우고 시작한다.

### 0:00 — 상황 설명 (20초)

> "실제 팀 프로젝트입니다. 실시간 결과 화면을 만든 브랜치고, PR을 올리기 직전 상태입니다."

터미널에 다음을 친다.

```bash
cd pulse-frontend
git status
git log --oneline origin/dev..HEAD
```

커밋 12개가 쌓인 것을 보여준다.

### 0:25 — 기준 문서 보여주기 (25초)

> "이 팀은 컨벤션을 CLAUDE.md에 적어 놨습니다. 도구는 이걸 기준으로 씁니다."

```bash
head -30 CLAUDE.md
```

"코드 규칙" 섹션까지 스크롤해서 `any` 금지, 절대경로 규칙이 적힌 부분을 잠깐 보여준다.

### 0:50 — 실행 (15초)

```
/branch-review:review
```

> "명령 하나입니다. 비교 기준 브랜치는 자동으로 찾습니다."

### 1:05 — 수집 결과 (25초)

`TARGET`과 `CONVENTION SOURCES` 섹션을 화면에 두고 설명한다.

> "`origin/dev`와의 분기점을 자동으로 잡았고요. 여기가 중요한데, CLAUDE.md를 기준 문서로 잡았고 `.prettierrc`랑 커밋 훅은 **제외 목록**으로 읽었습니다. 포매터가 자동으로 고치는 건 지적하면 안 되니까요."

### 1:30 — 리포트 1·2부 (35초)

> "리포트는 항상 네 부분입니다."

변경점 요약을 지나 컨벤션 위반 섹션에서 멈춘다.

> "여기 보시면 근거가 CLAUDE.md 원문 인용입니다. 이게 1차입니다. 반박하려면 문서를 고쳐야 합니다."

### 2:05 — 리포트 3부, 핵심 (40초)

`?submitted=1` 지적에서 멈춘다.

> "이건 컨벤션 위반은 아닙니다. 그래서 제안으로 나왔습니다."

> "제출하면 URL에 `submitted=1`이 붙고 그걸로 배너를 띄우는데, 이 값을 떼는 코드가 없습니다. 링크 저장했다 다시 열면 배너가 또 뜹니다."

> "그런데 같은 파일 주석에는 정확히 그 상황을 피하려고 이 방식을 골랐다고 적혀 있습니다. 의도랑 구현이 어긋난 거죠. 코드만 봐서도, 주석만 봐서도 안 보이고 겹쳐 읽어야 보입니다."

### 2:45 — 총평 (15초)

> "필수 0건이라 머지 가능으로 나왔고, 잘된 부분도 한 줄 짚어 줍니다. 지적만 나열된 리뷰는 다음번에 안 돌리게 되니까요."

### 3:00 — 마무리

> "PR 올리기 전에 이거 한 번 돌리는 게 이 도구의 용도입니다."
