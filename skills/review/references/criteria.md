# 리뷰 기준

이 도구가 무엇을 근거로 무엇을 지적하는지 정의한다. 리뷰의 설득력은 지적의 날카로움이 아니라 **근거의 출처가 분명한 데서** 나온다.

## 왜 두 층으로 나누는가

리뷰가 신뢰를 잃는 전형적인 방식은 "팀이 합의한 규칙"과 "리뷰어 개인의 취향"이 같은 목록에 섞여 나오는 것이다. 받는 쪽은 어느 것이 협상 불가이고 어느 것이 의견인지 구분할 수 없고, 결국 전부 의견으로 취급하게 된다.

그래서 이 도구는 근거의 출처로 층을 나눈다.

| | 1차 | 2차 |
|---|---|---|
| 근거 | 팀이 문서로 합의한 규칙 | 일반적인 통념·경험칙 |
| 반박 방법 | 문서를 고친다 | 그냥 다르게 판단하면 된다 |
| 기본 태도 | 고쳐야 한다 | 고려해 봐라 |
| 인용 형태 | 규칙 원문 그대로 | 실패 시나리오 |

**어느 층인지 헷갈리면 2차다.** 1차로 잘못 올린 지적은 없는 규칙을 만들어내는 셈이고, 2차로 잘못 내린 지적은 그냥 한 번 더 말하면 된다. 오류의 비용이 비대칭이다.

## 1차 — 컨벤션 위반

### 기준의 출처

우선순위 순서다. 위쪽이 아래쪽을 이긴다.

1. `.claude/review-rules.md` — 이 도구를 위해 작성한 전용 규칙
2. `CLAUDE.md`, `AGENTS.md`, `CONTRIBUTING.md` — 프로젝트 문서
3. `.github/PULL_REQUEST_TEMPLATE.md` — PR에 요구되는 항목

### 판정 가능한 규칙만 사용한다

문서의 모든 문장이 규칙은 아니다. **위반 여부를 코드만 보고 O/X로 답할 수 있는가**가 유일한 기준이다.

| 문서의 문장 | 규칙인가 | 이유 |
|---|---|---|
| "`any`는 금지" | O | 코드에 있거나 없다 |
| "import는 절대경로 `@/` 사용, `../../` 금지" | O | 경로 문자열로 판정된다 |
| "컨트롤러에 비즈니스 로직을 넣지 않는다" | O | 경계가 흐리지만 명백한 위반은 잡힌다 |
| "가독성 좋게 작성한다" | X | 판정 불가 |
| "적절히 분리한다" | X | '적절히'의 기준이 없다 |
| "성능을 고려한다" | X | 판정 불가 |

판정 불가한 문장은 1차에서 제외한다. 관련된 실제 문제를 발견했다면 2차로 낸다.

### 검사 대상 축

문서에 해당 규칙이 있을 때만 검사한다. 없는 축은 통째로 건너뛴다.

| 축 | 예시 |
|---|---|
| 커밋 메시지 | Conventional Commits 형식, subject 길이, body 필수 여부, type 목록 |
| 브랜치 | 네이밍 패턴, 통합 브랜치 직접 커밋 금지 |
| 파일·디렉토리 | 파일명 규칙, 폴더 구조, 파일명과 export 이름의 일치 |
| 네이밍 | 핸들러 `handle*`, 콜백 prop `on*`, 도메인 용어 충돌 회피 |
| 금지 문법 | `any`, 2단계 이상 상대경로, 엔티티 직접 노출, 평문 비밀번호 |
| 구조 | 레이어 분리, 관심사 격리, 클라이언트/서버 경계 |
| 보안·시크릿 | 커밋 금지 파일, 하드코딩된 키 |
| PR | 템플릿 항목, 제목 형식, 이슈 참조 |

### 심각도

| 표기 | 조건 |
|---|---|
| `[필수]` | 문서에 "금지"·"반드시"·"해야 합니다"로 적혔거나, 위반 시 동작이 깨지거나 보안 문제가 생김 |
| `[권장]` | 위반이 맞지만 동작에는 지장이 없고, 문서 표현도 강제형이 아님 |

## 2차 — 개선 제안

컨벤션이 침묵하는 영역이다. 코드는 돌아간다. 그럼에도 더 나은 방법이 있을 때 낸다.

### 우선순위

위에서부터 본다. 아래로 갈수록 취향에 가까워지므로, 아래 항목만으로 리뷰를 채우지 않는다.

1. **정확성** — 특정 입력·상태에서 잘못된 결과나 크래시. 실패 시나리오를 구체적으로 못 쓰면 내지 않는다
2. **누수·정리 누락** — 타이머, 구독, 커넥션, 파일 핸들
3. **경계 조건** — 빈 배열, `null`, 0, 동시 요청, 네트워크 실패
4. **중복** — 이미 있는 함수를 다시 구현했거나, 같은 코드가 세 곳 이상
5. **성능** — N+1 쿼리, 불필요한 리렌더, 큰 반복 안의 비싼 연산. 실제로 커질 수 있는 경우만
6. **테스트 공백** — 새 분기 로직에 테스트가 없음
7. **가독성** — 이름이 하는 일과 다르거나, 중첩이 과도

### 내지 않아야 할 것

- 포매터·린터가 자동으로 고치는 항목 (세미콜론, 따옴표, 들여쓰기, import 정렬)
- 취향 차이인 동등한 대안 (`for` vs `map`처럼 결과가 같은 것)
- 이번 변경과 무관한 기존 코드. 변경분이 그 코드를 실제로 악화시킬 때만 언급한다
- 이 변경 범위를 넘는 아키텍처 재설계 제안. 별도 이슈로 제안하되 리뷰 본문에 섞지 않는다
- 근거를 "일반적으로 좋다"로밖에 못 대는 것

### 심각도

전부 `[제안]`이다. 2차는 정의상 강제할 근거가 없다.

예외 — 2차에서 **명백한 버그**를 발견하면 `[필수]`로 올린다. 컨벤션에 없더라도 깨진 코드는 깨진 코드다. 이때는 근거 자리에 재현 조건을 구체적으로 쓴다.

## 지적 하나의 형식

세 요소를 모두 갖춘다. 하나라도 못 채우면 그 지적은 낼 준비가 안 된 것이다.

```
### [심각도] 한 줄 요약 — 파일:라인

> 근거: (1차) 문서명 + 규칙 원문 인용
>       (2차) 어떤 조건에서 무엇이 잘못되는지

현재 코드 / 개선안 코드
```

**한 줄 요약**은 문제를 말한다. "타입 개선 필요"가 아니라 "`any`로 응답을 받아 런타임에 형태 검증이 사라짐"이다.

**개선안**은 그대로 붙여넣을 수 있어야 한다. "타입을 명시하세요"는 개선안이 아니다.

## 자기 점검

보고 전에 확인한다.

- [ ] 1차의 모든 항목에 문서 원문을 인용했는가
- [ ] 2차의 모든 항목에 구체적인 실패 시나리오나 이득이 있는가
- [ ] 포매터가 잡을 항목이 섞이지 않았는가
- [ ] 읽지 않은 파일을 리뷰하지 않았는가
- [ ] 건수를 채우려고 억지 지적을 넣지 않았는가
- [ ] 총평에 머지 가능 여부가 있는가
