# 2차 체크리스트 — 백엔드 (Java / Spring Boot / JPA)

해당하는 항목만 쓴다. Spotless·Checkstyle이 잡는 포맷 항목은 제외한다.

## 레이어

- 컨트롤러에 비즈니스 로직·조건 분기가 들어갔는가
- 서비스가 `HttpServletRequest`·`ResponseEntity` 같은 웹 계층 타입을 다루는가
- 리포지토리 인터페이스에 도메인 규칙이 새어 들어갔는가
- 엔티티가 컨트롤러 요청·응답에 그대로 노출되는가

## JPA

- `@ManyToOne`/`@OneToOne`의 기본 `fetch`가 `EAGER`로 남아 있는가 (명시적으로 `LAZY` 지정)
- 목록 조회에서 연관 엔티티를 순회해 N+1이 발생하는가. fetch join·`@EntityGraph`가 필요한 자리인가
- `@Transactional`이 읽기 전용 메서드에 `readOnly = true` 없이 붙었는가
- 트랜잭션 경계 밖에서 지연 로딩 프록시에 접근하는가 (`LazyInitializationException`)
- 양방향 연관에서 연관관계 편의 메서드 없이 한쪽만 설정하는가
- `equals`/`hashCode`를 엔티티에 구현하면서 가변 필드를 썼는가
- `save()`를 이미 영속 상태인 엔티티에 호출하는가 (더티 체킹으로 충분한 자리)

## 트랜잭션

- 같은 클래스 내부 호출로 `@Transactional`이 프록시를 타지 않는가
- 트랜잭션 안에서 외부 API 호출·파일 IO를 하는가 (커넥션을 오래 잡는다)
- 여러 저장 작업이 하나의 트랜잭션으로 묶여야 하는데 나뉘어 있는가

## 검증과 오류

- 요청 DTO에 `@Valid`와 제약 애너테이션이 붙었는가
- 컨트롤러마다 `try/catch`가 흩어져 있는가. `@RestControllerAdvice`로 모을 자리인가
- 예외 메시지에 내부 구조(테이블명, 쿼리, 스택)가 노출되는가
- `Optional`을 `get()`으로 바로 여는가 (`orElseThrow`에 의미 있는 예외를 담는다)
- 도메인 예외와 시스템 예외가 같은 상태 코드로 뭉뚱그려지는가

## 보안

- 비밀번호가 평문으로 저장·비교되는가 (`BCryptPasswordEncoder`)
- 인증만 하고 소유권 인가를 확인하지 않는 리소스 접근이 있는가 (`ownerId == 현재 사용자`)
- 시크릿이 `application.yml`에 하드코딩됐는가
- 로그에 토큰·비밀번호·개인정보가 찍히는가
- 문자열 연결로 만든 쿼리가 있는가

## API 계약

- 응답 필드명·타입이 프론트의 목 스키마·API 명세와 일치하는가
- 상태 코드가 의미에 맞는가 (생성 201, 권한 없음 403, 미인증 401)
- 페이지네이션 응답 형태가 다른 엔드포인트와 일관된가
- 필드를 추가·삭제하면서 반대편 레포에 반영했는가

## 동시성

- 공유 가변 상태를 필드로 들고 있는가 (`@Service`는 싱글턴이다)
- 재고 차감·카운터 증가 같은 갱신에 락·원자 연산이 필요한가
- `SimpleDateFormat` 등 스레드 안전하지 않은 객체를 필드로 공유하는가

## 성능

- 반복문 안에서 쿼리를 호출하는가
- 전체 조회 후 애플리케이션에서 필터링하는가 (쿼리로 내릴 수 있는가)
- 대량 삽입을 건별 `save()`로 처리하는가
- 인덱스가 없는 컬럼으로 조회하는 새 쿼리인가

## 테스트

- 슬라이스 테스트(`@WebMvcTest`, `@DataJpaTest`)로 충분한 자리에 `@SpringBootTest`를 썼는가
- 테스트가 실행 순서·기존 데이터에 의존하는가
